# 常见报错与排查手册

> 适用范围：当前仓库 `langchain-starter` 的学习与实操  
> 目标：遇到问题时，先快速定位是环境、依赖、模型、RAG、Tool、API 还是前端问题

---

## 排查原则

排查时先别急着改很多代码，先回答这 4 个问题：

1. 这是启动失败，还是运行到一半失败？
2. 这是环境问题，还是业务逻辑问题？
3. 这是模型调用失败，还是本地代码失败？
4. 这是第一次就失败，还是改了代码后才失败？

建议按这个顺序排：

1. 环境变量
2. 依赖安装
3. 最小脚本是否能跑
4. RAG 是否能单独跑
5. Agent 是否能单独跑
6. API 是否能单独跑
7. 前端是否只是联调问题

---

## 一、环境与依赖问题

### 1. `ModuleNotFoundError`

常见现象：

- 找不到 `langchain`
- 找不到 `dotenv`
- 找不到 `langchain_huggingface`
- 找不到 `faiss`

常见原因：

- 依赖没有安装
- 没有进入正确的虚拟环境
- `requirements.txt` 没有完整安装

排查步骤：

1. 确认当前虚拟环境是否激活
2. 重新安装 `requirements.txt`
3. 如果是新增依赖，确认它是否已经写入依赖文件

建议优先验证：

- 先跑 `project/01/hello.py`
- 如果最小脚本都跑不通，先别继续排查 Agent

### 2. `.env` 没生效

常见现象：

- `API_KEY` 为空
- `BASE_URL` 为空
- 模型初始化时报认证错误

常见原因：

- `.env` 文件不在项目根目录
- 变量名写错
- 变量值有多余空格或引号问题

排查步骤：

1. 确认项目根目录存在 `.env`
2. 确认变量名和代码里读取的一致
3. 确认 `load_dotenv()` 已执行
4. 临时打印变量是否为空

注意：

- 不要把真实密钥提交到仓库

### 3. Python 版本或依赖版本不兼容

常见现象：

- 安装时报编译错误
- 某些包导入路径和示例不一致
- LangChain API 与代码示例不匹配

常见原因：

- 本地 Python 版本过新或过旧
- 不同教程对应的 LangChain 版本不同

排查步骤：

1. 先以当前仓库 `requirements.txt` 为准
2. 不要同时参考多个旧教程直接改代码
3. 如果导入路径和教程不同，优先以本仓库可运行代码为准

## 二、模型调用问题

### 4. 模型调用时报认证或 401/403 错误

常见原因：

- `API_KEY` 错误
- `BASE_URL` 错误
- 模型名不可用
- 服务商权限不足

排查步骤：

1. 检查 `.env` 中的 `API_KEY`
2. 检查 `BASE_URL`
3. 检查代码中的模型名是否和你当前服务一致
4. 先用 `project/01/hello.py` 验证最小调用

建议：

- 先确认“模型能聊起来”，再继续排查 RAG / Agent

### 5. 模型调用超时或网络异常

常见现象：

- 请求卡住
- 超时
- 连接失败

常见原因：

- 网络不稳定
- 第三方模型服务异常
- 请求链路过长

排查步骤：

1. 先重试最小脚本
2. 如果最小脚本也失败，更可能是网络或服务问题
3. 如果只有 Agent 慢，检查是否调用了多个工具或检索步骤

### 6. 输出质量很差，但程序没报错

常见原因：

- prompt 不清晰
- 模型不适合当前任务
- 工具描述不清晰
- RAG 检索内容质量差

排查步骤：

1. 先用最小 prompt 测试模型基础能力
2. 再检查系统提示词是否过长或冲突
3. 如果是 RAG 问题，先看检索到的文档片段
4. 如果是 Agent 问题，先看有没有选错工具

## 三、RAG 问题

### 7. 向量库加载失败

常见现象：

- `FAISS.load_local(...)` 报错
- 提示索引文件不存在

常见原因：

- 首次运行时向量库还没生成
- 索引目录被删了
- 路径配置不对

排查步骤：

1. 确认向量库目录是否存在
2. 如果不存在，先跑构建向量库的脚本
3. 检查路径是否指向正确目录

关联文件：

- `project/03/rag_qa.py`
- `project/03/rag_qa_local_embedding.py`
- `project/05/cust_service_agent_cli.py`

### 8. RAG 能跑，但回答总是不准

常见原因：

- FAQ 写得不清楚
- chunk 太大或太小
- top-k 不合适
- 问题表达和知识库表述差异太大

排查步骤：

1. 打印或查看检索出的文档片段
2. 问自己：检索阶段就错了，还是生成阶段才错？
3. 调整 chunk size 和 `k`
4. 优化 FAQ 文档表达

一个很实用的判断方法：

- 如果检索片段就不相关，是检索问题
- 如果检索片段相关，但最终回答偏了，是生成或 prompt 问题

### 9. 首次运行本地 embedding 很慢

常见原因：

- 首次下载本地 embedding 模型
- CPU 运行向量化速度较慢

说明：

- 这通常不是 bug
- 首次慢，后续会好很多

建议：

- 先耐心等首次初始化完成
- 大文档不要一上来就塞太多

## 四、Tool 与 Agent 问题

### 10. Agent 不调用工具，直接瞎答

常见原因：

- tool 描述不清楚
- system prompt 没强调工具使用边界
- 模型认为自己可以直接回答

排查步骤：

1. 检查 tool docstring 是否清晰
2. 检查 prompt 是否要求“相关问题优先使用工具”
3. 给更明显的测试问题，看 agent 是否还是不调用

修复方向：

- 改工具说明
- 改系统提示词
- 缩小模型自由发挥空间

### 11. Agent 调错工具

常见原因：

- 两个工具的用途描述过于接近
- 用户输入本身模糊
- tool 返回格式不利于继续推理

排查步骤：

1. 比较各工具描述是否重叠
2. 给每个工具补充更明确的适用场景
3. 设计边界测试题，专门测试工具路由

### 12. Tool 参数提取失败

常见现象：

- 订单号没识别出来
- 城市名提取错了
- 表达式传错

常见原因：

- 用户输入格式不稳定
- 工具入参设计太脆弱

排查步骤：

1. 对用户输入做更稳的规范化处理
2. 为常见变体准备兜底逻辑
3. 对 mock 数据设计更多非标准输入测试

关联场景：

- `query_order_status`
- `query_shipping_info`

### 13. Tool 报错后整个 Agent 体验很差

常见原因：

- 工具异常没有被捕获
- 错误信息直接暴露给用户

排查步骤：

1. 给 tool 增加 `try/except`
2. 返回用户可理解的兜底信息
3. 日志里保留技术细节，用户界面里只保留友好提示

## 五、Memory 与多轮问题

### 14. 多轮对话里忘记订单号

常见原因：

- 会话历史没有正确保存
- 历史被裁剪太早
- 没有单独保存关键状态

排查步骤：

1. 检查 session 是否真的复用了同一个 `session_id`
2. 检查消息历史是否被覆盖
3. 检查关键字段是否只靠自然语言历史保存

更稳的做法：

- 订单号这类核心字段最好单独保存为状态

### 15. 多轮对话越聊越乱

常见原因：

- 历史消息太长
- 无关上下文太多
- 同时混入多个订单、多个意图

排查步骤：

1. 限制历史长度
2. 在关键转折处做状态重置
3. 避免把所有历史原封不动无限拼接

## 六、API 问题

### 16. API 能启动，但 `/chat` 报错

关联文件：`project/06/api_server.py`

常见原因：

- 请求体格式不对
- `session_id` 或 `message` 缺失
- agent 返回结果结构和预期不一致

排查步骤：

1. 检查请求 JSON 是否包含：
   - `session_id`
   - `message`
2. 检查 `agent.invoke(...)` 返回结果结构
3. 检查 `result["messages"][-1]` 是否一定存在

### 17. 多个会话串了

常见原因：

- session_id 没区分
- 所有请求都在复用同一会话存储

排查步骤：

1. 检查前端是否真的传了不同 `session_id`
2. 检查后端消息存储是否按 `session_id` 分组

### 18. 日志里有记录，但看不出问题

常见原因：

- 没记录关键字段
- 没有 trace_id 串联请求

排查思路：

1. 先看是否有 `trace_id`
2. 看用户问题、回复摘要、工具调用次数是否都被记录
3. 如果日志太少，补充关键埋点

---

## 七、前端联调问题

### 19. 页面能打开，但发不出消息

常见原因：

- 前端请求地址不对
- 后端没启动
- 跨域或网络配置问题

排查步骤：

1. 先确认后端接口单独可用
2. 再确认前端请求地址是否正确
3. 看浏览器控制台和网络请求状态

### 20. 页面显示异常，但后端其实已经返回了

常见原因：

- 前端没正确处理响应格式
- 消息渲染逻辑有问题

排查步骤：

1. 确认后端响应字段名
2. 确认前端读取的是同样的字段
3. 区分是“接口错了”还是“界面没显示出来”

---

## 八、评估问题

### 21. 评估结果看起来“全都差不多”

常见原因：

- 测试题太少
- 题目区分度不够
- 没分类统计

排查步骤：

1. 扩展测试集
2. 把题目分成 FAQ、订单、物流、多轮、异常输入
3. 分类看失败原因

### 22. 修了代码，但评估没明显变好

常见原因：

- 改动没有命中真正瓶颈
- 评估集不够敏感

排查步骤：

1. 先找最典型的失败案例
2. 只修 1-2 类关键问题
3. 重跑并做前后对比

## 快速定位表

### 如果最小脚本都跑不通

- 优先看：
  - 依赖
  - `.env`
  - 模型配置

### 如果最小脚本能跑，RAG 不行

- 优先看：
  - 文档路径
  - 向量库
  - embedding
  - 检索参数

### 如果 RAG 能跑，Agent 不稳定

- 优先看：
  - tool 描述
  - tool 参数处理
  - system prompt
  - 多工具边界

### 如果 CLI 正常，API 不正常

- 优先看：
  - 请求体格式
  - session_id
  - 返回结构

### 如果 API 正常，前端不正常

- 优先看：
  - 请求地址
  - 响应字段映射
  - 浏览器控制台报错

---

## 建议你长期保留的排查习惯

- 每次只改一个主要变量，不要同时改很多地方
- 先保留一个最小可运行版本
- 多记录失败案例，不要只记录成功演示
- 先确认“哪一层坏了”，再修那一层
- 排查时优先从最小链路开始回退
